# Match result confirmation gates rating

`completeMatch` let any one of a Match's four seated Users (or the Organizer) unilaterally mark it completed, which synchronously applied Glicko-2 rating updates to all four — one person's tap decided four Ratings from a self-reported score with no check from anyone else. **A Match now rates only once every seated User on its two Game teams has confirmed the entered result**: the User who enters the Set that first produces a Match result is confirmed automatically, each remaining seated User confirms once via a new door, and the last confirmation triggers the existing complete-and-rate transaction with no separate manual step. The Organizer keeps the existing unilateral force-complete power as an override for a Match where a player will not respond.

Confirmation count is tracked in a new `match_result_confirmations` table (one row per Match per User), not on `match.status`. `MatchStatusEnum.CONFIRMED` was already declared in the schema and had never been read or written anywhere in the application; it stays deliberately unused rather than repurposed for this feature, because a Match with some but not all confirmations needs a state that is not "confirmed", and overloading one word for both a stored Match status and a per-User act reads wrong to the next engineer. A future use of `CONFIRMED` should not assume it means "result confirmation" without re-reading this decision.

**Considered Options**: reuse `MatchStatusEnum.CONFIRMED` as the stored mid-state — rejected for the naming collision above. Majority (3-of-4) confirmation — rejected: a bare majority lets two Users outvote a dissenting third without the fourth weighing in, and unanimous is the trust story the product wants ("the other three confirm"). Auto-complete after a timeout with no response — rejected for this slice: no reminder or notification system exists yet to make a timeout meaningful, and a silent timeout defeats the point of asking for confirmation.

**Dispute and rating reversal** ("report a wrong score" after a Match has already rated) is resolved as **gated self-service reversal**: the Organizer may reopen a completed Match only when none of its four seated Users has a *later* Rated Match — Glicko-2 updates are sequential, so restoring stored before-values is only correct when nothing has been built on top of them since. When clean, reversal restores all four Ratings to their before-values, deletes the four rating events, clears `match_result_confirmations`, and drops `match.status` back to `pending` — which re-derives the existing `needs_results` phase and re-enters the same confirmation flow from zero on the next score entry, rather than inventing a second lifecycle. When not clean, self-service reversal is refused; correction becomes a manual/support path outside this ADR's scope. See `.scratch/game-details-redesign/spec.md` for the full mutation shape and eligibility rule.
